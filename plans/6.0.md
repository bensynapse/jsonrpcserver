# Plan: jsonrpcserver 6.0

Tracking issue: [#320](https://github.com/bensynapse/jsonrpcserver/issues/320). Public summary:
[docs/roadmap.md](../docs/roadmap.md). Started 2026-11-06, from 5.1.0 (`dddf0e3`).

## Branches

- `main` is 6.0 development from now on. `__version__` is `6.0.0.dev0` until the first release candidate.
- `release/5.x` (from the 5.1.0 tag) carries 5.x fixes. It has the same protection as main ("CI OK" required,
  admins included, no force push), and `release.yml` already accepts tags on `release/` branches.
- Every change reaches main through a pull request with green "CI OK", one increment at a time.

## What 6.0 is for

Three things hold jsonrpcserver back, and each needs a breaking change:

1. **oslash.** `Success`, `Error` and the dispatch functions return oslash `Left` and `Right` objects. oslash's last
   release for Python 3.8 to 3.11 is from 2020, its newer releases need 3.12, and it isn't maintained.
2. **jsonschema.** It takes about three quarters of the dispatch time for a small method (measured 2026-10-06).
   It also pulls in a Rust extension through `referencing` and `rpds-py`, to check five fields.
3. **Defaults.** A server that follows the quickstart accepts batches of any size and `NaN` in requests.

## Decisions

| | Decision | Why |
|---|---|---|
| D1 | `requires-python >=3.11` | 3.8, 3.9 and 3.10 have reached end of life (3.10 in October 2026). 3.11 brings `X \| Y` unions, `Self` and faster code. |
| D2 | `SuccessResult` and `ErrorResult` become frozen dataclasses. `Result = SuccessResult \| ErrorResult`. `Success`, `Error` and `InvalidParams` keep their signatures. | Code that only uses `Success`, `Error` and `dispatch` keeps working. `isinstance(result, ErrorResult)` replaces `isinstance(result, Left)`. |
| D3 | Responses become `SuccessResponse \| ErrorResponse` dataclasses. `dispatch_to_response` returns one response, a list, or `None` for no response. | The same shape as results, no wrapper type. `None` replaces the `NoResponse` sentinel class. |
| D4 | No runtime dependencies. A hand-written check replaces jsonschema. The `validator` hook stays, with the same contract: raise to reject. | Faster, smaller install. The check covers exactly what `request-schema.json` covered, proven by the conformance tests. |
| D5 | `max_batch_size` defaults to 100. `None` turns the limit off. | A batch is work the client chooses. 100 is far above normal use and far below an abuse. |
| D6 | The default deserializer rejects `NaN`, `Infinity`, `-Infinity` and numbers that overflow to infinity, with a Parse error. | They aren't JSON (RFC 8259 section 6), and strict clients reject them anyway. A custom `deserializer` can still accept them. |
| D7 | `Error`, `JsonRpcError` and `InvalidParams`: a non-integer code or a non-string message raises `TypeError`. `@method` raises `ValueError` for a name starting with `rpc.`. | 5.0.10 warned. The spec says MUST, and a warning that nobody reads still sends an invalid response. |
| D8 | `async_dispatch` and friends take `max_concurrency: int \| None = None`, a limit on the batch members that run at once. | A 100-member batch of slow async methods shouldn't open 100 database connections. |
| D9 | One `@method` decorator for sync and async functions. No `@async_method`. The sync and async dispatch functions take the same options with the same defaults. | 5.0.10 already accepts both kinds of function in `async_dispatch`. A second decorator would only split the registry. The sync `dispatch_to_response` defaults `deserializer` to `json.loads`, unlike the rest. It moves to `default_deserializer` with D6. |
| D10 | Remove `serialize_error`, `serialize_success` and `to_serializable_one` (in `response` and `main`), the aliases PR 296 brought back with a `DeprecationWarning`, and `ResponseType`. The `Method` and `Methods` re-exports in the dispatcher modules stay. | Deprecated since 5.0.10. The re-exports cost nothing and keep 5.0.9 imports working. |
| D11 | Rework `serve()`, don't remove it: it listens on localhost unless given a host. *(Changed 2026-11-06 from "remove".)* | The danger was that `serve()` listened on every interface by default, so a quickstart left running was open to the network. A localhost default fixes that. Removing it would have turned the README quickstart, the docs home page and the tested quickstart from 10 lines into about 25 of http.server code. bcb's advice (#255) was "rework or remove". |
| D12 | Before 6.0.0, release 5.2.0 from `release/5.x`. It warns (`FutureWarning`) when `serve()` is called without a host, and where code inspects `Left`/`Right` in a way that can be detected. | Upgrades shouldn't surprise anyone. |

## Increments

Each is one pull request into main. Each keeps every repo gate green: tests at 100% coverage, ruff, mypy, pyright
strict, the doc examples and `mkdocs build --strict`.

1. **Python 3.11.** Update `requires-python`, the classifiers, the CI matrix (3.11 to 3.14, plus 3.14t), tox and
   ruff's `target-version`. Then `ruff --fix` applies the UP rules, such as `Optional[X]` to `X | None`. The version
   becomes `6.0.0.dev0`.
2. **Results and responses without oslash** (D2, D3). The largest change. Tests move from `Left`/`Right` to the new
   types first, so the behaviour they check stays the same.
3. **Requests without jsonschema** (D4). Conformance tests first: every case `request-schema.json` accepts or rejects,
   run against both checks, then the switch.
4. **Safer defaults** (D5, D6, D7).
5. **Removals** (D10), **`serve()` on localhost** (D11) and **unified options** (D9).
6. **Async concurrency limit** (D8).
7. **Docs and release.** Migration guide from 5.x to 6.0, the changelog and the roadmap page. Then 5.2.0 on
   `release/5.x` (D12), and `6.0.0rc1` on main.

## Acceptance

- Code that only uses `@method`, `Success`, `Error` and `dispatch` runs unchanged on 6.0 (a test pins this).
- The package has no runtime dependencies.
- Dispatching a small method is at least twice as fast as on 5.1.0, measured the same way as in 2026-10.
- Every removed or changed name is in the migration guide, with the replacement.
- All repo gates are green on main, and `release/5.x` can still release.

## Risks

- **Users who inspect `Left`/`Right`.** `dispatch_to_response` users who unwrap results break. The migration guide
  shows both forms, and 5.2.0 warns first.
- **A hand-written validator can disagree with the schema.** Conformance tests run both checks over the same cases
  before jsonschema goes.
- **Default `max_batch_size` rejects a real use.** It's one keyword to raise or turn off, and the error says so.
